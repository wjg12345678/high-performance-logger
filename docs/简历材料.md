## 一段式项目介绍

该项目是一个面向高并发场景的 C++20 异步日志库，采用“日志器 + 输出端 + 后台线程”分层架构，支持日志分级、异步落盘、自定义输出端和阻塞/丢弃两种队列背压策略。核心数据通道使用基于 `CAS` 的有界无锁环形缓冲区，结合 `atomic::wait/notify` 降低多线程日志写入时的锁竞争；并通过与 `mutex + condition_variable` 基线的对照压测验证吞吐提升。

## 可直接贴进简历的描述

- 参考 `spdlog` 独立实现 C++20 高性能异步日志库，采用“日志器 + 输出端 + 后台线程”分层架构，支持日志分级、异步落盘和自定义输出端。
- 基于 `CAS` 设计有界无锁环形队列，结合 `atomic::wait/notify` 替代 `mutex/condition_variable`，解决多线程日志写入中的锁竞争问题，并通过单消费者模型保证落盘线程安全。
- 以 `mutex + condition_variable + deque` 为基线完成对照压测，在 `8` 线程 `160000` 条日志写入场景下，日志写入吞吐由约 `4.73e5 msg/s` 提升至约 `3.09e6 msg/s`，提升约 `554%`。

## 适合面试的一分钟口述稿

这个项目的出发点是同步日志在高并发场景下很容易因为共享锁成为瓶颈。我参考 `spdlog` 做了一个独立的 C++20 异步日志库，把整体拆成“日志器 + 输出端 + 后台线程”三层。核心优化点是把传统的 `mutex + condition_variable` 队列换成了基于 `CAS` 的有界无锁环形队列，并用 `atomic::wait/notify` 做线程唤醒；这样生产者线程只负责格式化和入队，后台线程顺序落盘，既减少了锁竞争，也保证了输出端的线程安全。为了证明优化有效，我又实现了一个同模型的互斥锁基线压测，在 `8` 线程 `160000` 条日志写入场景下，吞吐从大约 `4.73e5 msg/s` 提升到 `3.09e6 msg/s`。

## 面试追问时可展开的点

- 为什么选环形缓冲区：因为它有固定容量、预分配内存、缓存友好，更适合高频短消息场景。
- 为什么要做单消费者：因为文件写出需要顺序性，同时可以避免输出端自身再加锁。
- 为什么压测要用内存输出端：因为需要先隔离磁盘 I/O，只观察队列和线程同步带来的差异。
- 为什么要保留阻塞和丢弃两种策略：不同业务对“完整性”和“时延”偏好不同，日志库需要给使用方选择空间。
