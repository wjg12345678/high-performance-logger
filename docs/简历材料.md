# HLog 简历材料

这份文档用于快速整理 high-performance-logger 在简历和面试中的表达方式。项目不要写成“我实现了一个日志库”这么泛，而要突出异步写入、无锁队列、热路径优化、文件 sink、工程验证和边界意识。

## 1. 项目名称

推荐：

```text
HLog｜C++20 高性能异步日志库
```

也可以写：

```text
high-performance-logger｜基于无锁环形队列的 C++ 异步日志库
```

## 2. 一句话介绍

```text
基于 C++20 实现的异步日志库，采用多生产者单消费者模型和 CAS 无锁有界环形队列，将业务线程日志写入与后台 sink 输出解耦，支持日志分级、阻塞/丢弃背压、Flush/Stop 生命周期、文件轮转、格式化、CMake install/export 和多组 benchmark 验证。
```

## 3. 简历 Bullet 推荐

### 版本一：偏 C++ 并发

```text
- 设计并实现 C++20 异步日志库，采用 MPSC 模型和基于 CAS 的有界无锁环形队列承接多线程日志写入，通过槽位 sequence、acquire/release 内存序和 cache line 对齐降低锁竞争与 false sharing。
- 实现 AsyncLogger 生命周期管理，支持日志级别过滤、Block/DropNewest 背压、Flush 同步票据、Stop 两阶段关停和后台 sink 异常可观测，避免关闭阶段丢日志或悬挂写入。
- 优化 producer 热路径，使用 256B inline payload、std::to_chars 和 thread_local 线程 id 缓存减少短日志堆分配与流格式化开销，并通过吞吐、延迟、payload 和 file sink benchmark 量化效果。
```

### 版本二：偏工程化

```text
- 实现可复用 C++ 异步日志库，内置 ConsoleSink、FileSink、RotatingFileSink、MultiSink、PatternFormatter 和 LoggerConfig，支持 CMake install/export、最小 consumer 示例和 Docker/CI 验证。
- 建立性能验证体系，对比 mutex 队列、CAS 无锁队列、可选 spdlog 基线、producer 调用延迟、payload hot path 和真实文件落盘路径，输出 CSV/SVG/Markdown benchmark 报告。
- 明确异步日志生产化边界，补充队列满策略、flush 语义、sink 故障、进程崩溃丢失窗口、fsync 成本和接入规范，避免把性能样例夸大成所有场景结论。
```

### 版本三：短版

```text
- 基于 C++20 实现高性能异步日志库，使用 CAS 无锁有界环形队列、多生产者单消费者模型、后台批量写 sink、Flush/Stop 生命周期和多组 benchmark，优化多线程日志写入下的锁竞争和 producer 热路径开销。
```

## 4. 30 秒开场

```text
HLog 是我做的一个 C++20 异步日志库，核心目标是降低高并发业务线程写日志时的锁竞争和热路径开销。它采用多生产者单消费者模型，业务线程先经过日志级别过滤和 payload 构造，再写入 CAS 无锁有界环形队列，后台线程统一 drain 队列并写到 Console/File/Rotating/MultiSink。项目还补了 Flush、Stop、队列满策略、sink 异常处理、CMake install/export 和多组 benchmark。
```

## 5. 1 分钟展开

```text
这个项目我最想讲两个点。第一是并发队列：没有用 mutex + deque，而是实现了基于槽位 sequence 的有界无锁环形队列。生产者通过 CAS 抢占写位置，消费者单线程顺序取出，配合 acquire/release 内存序保证消息发布可见性。第二是日志热路径：短日志使用 256B inline buffer 和 std::to_chars，减少 ostringstream 和堆分配；线程 id 用 thread_local 缓存。为了避免只讲理论，我做了吞吐、producer 延迟、payload、file sink 和可选 spdlog 对比 benchmark，并在文档里说明测试口径和边界。
```

## 6. 面试主动承认的边界

```text
HLog 当前可以作为可复用异步日志库接入项目，但我不会说它已经完整替代 spdlog/log4j 这类成熟生态。它还缺结构化日志、异步压缩、远端 sink、日志采样、动态配置、跨进程聚合和更完整的崩溃恢复能力。性能数据也只代表当前机器和测试口径，尤其 file sink 会受文件系统缓存、磁盘和负载影响。
```

## 7. 最适合被问的点

- 无锁环形队列为什么需要 sequence。
- acquire/release 内存序怎么理解。
- `Block` 和 `DropNewest` 怎么取舍。
- `Flush()` 为什么要通过后台线程完成。
- `Stop()` 如何避免生产者正在写时析构。
- 异步日志什么时候会丢。
- 为什么 file sink benchmark 不一定稳定提升。
- 为什么不能只看 QPS。

## 8. 不建议写法

| 不建议 | 原因 |
| --- | --- |
| “性能超过 spdlog 十倍” | 过度绝对，容易被测试口径追问 |
| “无锁所以一定更快” | 低并发或不同负载下 mutex 可能更简单更快 |
| “异步日志不会丢日志” | 崩溃、DropNewest、未 fsync 都可能丢 |
| “生产级日志系统” | 缺结构化、采样、远端传输、动态配置等生态能力 |

## 9. 最终推荐写法

```text
HLog｜C++20 高性能异步日志库
基于 C++20 实现异步日志库，采用多生产者单消费者模型和 CAS 无锁有界环形队列优化多线程写日志锁竞争；实现日志分级、Block/DropNewest 背压、Flush/Stop 生命周期、Console/File/Rotating/MultiSink、PatternFormatter、CMake install/export；通过 mutex 队列、可选 spdlog、producer 延迟、payload hot path 和 file sink benchmark 验证性能收益与边界。
```
