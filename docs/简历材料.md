## 一句话项目介绍

参考 `spdlog` 设计实现的 C++20 异步日志库，基于 `CAS` 无锁环形队列优化高并发日志写入热路径，并补齐 formatter、sink 组合、安装导出和自动化验证能力。

## 一段式项目介绍

该项目是一个面向高并发场景的 C++20 异步日志库，采用“日志器 + 输出端 + 后台线程”分层架构，支持日志分级、异步落盘、阻塞/丢弃两种队列背压策略以及 `ConsoleSink / FileSink / RotatingFileSink / MultiSink` 等内置输出端。核心数据通道使用基于 `CAS` 的有界无锁环形缓冲区，结合 `atomic::wait/notify` 与 `thread_local` 线程 ID 缓存降低多线程日志写入时的热路径开销；同时将 producer 侧 payload 构造改成 `256B` inline payload + `std::to_chars` 直接追加，减少常见短日志场景下的额外堆分配和流格式化开销。仓库当前还提供 `PatternFormatter`、`LoggerConfig`、`CMake install/export`、最小 consumer、GitHub Actions、`ASAN/UBSAN/TSAN`、install smoke test 以及 Docker 服务示例，已经形成可复用、可验证的工程闭环。

- 参考 `spdlog` 设计实现 C++20 异步日志库，采用“日志器 + 输出端 + 后台线程”架构，支持 `PatternFormatter`、`LoggerConfig`、`Console/File/Rotating/MultiSink`、`CMake install/export` 与 Docker 服务示例。

- 参考 `spdlog` 设计实现 C++20 异步日志库，采用“日志器 + 输出端 + 后台线程”分层架构，支持日志分级、异步落盘、阻塞/丢弃两种背压策略以及 `ConsoleSink / FileSink / RotatingFileSink / MultiSink`。

## 口述稿

这个项目的核心目标是解决高并发场景下日志路径容易因为共享锁成为瓶颈的问题。我参考 `spdlog` 做了一个 C++20 异步日志库，把整体拆成“日志器 + 输出端 + 后台线程”三层。最核心的优化是把传统的 `mutex + condition_variable` 队列换成了基于 `CAS` 的有界无锁环形队列，并用 `atomic::wait/notify` 做线程唤醒，同时把线程 ID 获取改成 `thread_local` 缓存，减少每条日志的固定热路径开销；另外又把 producer 侧 payload 构造从 `std::ostringstream` 改成 `256B` inline payload + `std::to_chars` 直接追加，尽量让常见短日志不再额外堆分配。在当前机器 `8` 线程 `160000` 条日志、`1` 次 warm-up + `5` 次测量的中位口径下，吞吐从约 `1.38e6 msg/s` 提升到 `4.35e6 msg/s`，单次 `Log()` 平均延迟从约 `9.40 us` 降到 `1.52 us`。除了性能部分，我还补了 `PatternFormatter`、`LoggerConfig`、可组合 sink、`CMake install/export`、最小 consumer、CI、sanitizer 和 Docker 服务示例，让它从 benchmark demo 变成了一个可复用、可验证的异步日志组件。

## 面试追问时可展开的点

- 为什么选有界环形缓冲区：固定容量、预分配内存、缓存友好，更适合高频短消息场景。
- 为什么选单消费者：输出端天然需要顺序性，同时可以避免 file sink 自身再加锁。
- 为什么压测先用内存 sink：先隔离磁盘 I/O，只观察队列和线程同步带来的差异。
- 为什么还要优化 payload：lock-free queue 只能解决并发同步问题，producer 侧的格式化和分配同样会成为瓶颈。
- 为什么要补 `PatternFormatter` 和 `LoggerConfig`：从“能跑 benchmark”升级成“能被其他项目直接接入”的关键一步。
- 为什么要做 install/export 和 consumer：证明它不是仓库内自用代码，而是一个可复用组件。
- 为什么要补 Docker 服务示例：说明项目不仅有 micro-benchmark，也能在真实服务链路里启动、接请求并输出日志。
- 为什么真实 file sink 结果不直接写成稳定收益：文件系统路径噪声更大，应该单独报告方法和口径，而不是把本机结果包装成普适结论。

## 避坑表述

- 建议写：`高性能异步日志库`、`高并发日志核心组件`。
- 不建议写：`完全替代 spdlog`、`成熟商业日志平台`、`已在生产大规模使用`。
- 写性能数字时要明确边界：`当前机器`、`中位值`、`内存 sink`、`producer hot path`。
- 真实 file sink 部分建议写成：`单独报告真实写路径 benchmark，用于验证方法与工程口径`，不要写稳定正向百分比。
